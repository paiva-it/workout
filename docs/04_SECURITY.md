# Authentication and public-source boundary

Public source does not mean public data. All personal API routes require a valid server-side session and owner checks; only login and minimal health endpoints are public. No signup or password recovery by email is required for this single-user app.

## Passwords and bootstrap

Use Argon2id with a random salt generated by the library. Start with memoryCost 65536 KiB, timeCost 3, parallelism 1; benchmark on the actual host and document the chosen parameters. Do not go below the OWASP minimum of 19456 KiB, timeCost 2, parallelism 1. Verify using the library, and rehash on login when the stored parameters are below the configured policy. Never use SHA-256 for passwords.

Consume the supplied bootstrap credentials only in a one-time backend script from stdin or a protected file, not a frontend bundle, image layer, command argument, CI log or tracked environment file. The initial password must match the user's supplied value. Existing account => no-op; never reset it during redeploy or seed. Password change requires current password, offers a stronger replacement, revokes other sessions and preserves the requested initial login until the user changes it. A server-side CLI reset must accept secret input without echo. Do not force a first-login change not requested by the user.

## Sessions

Prefer opaque random tokens (at least 32 random bytes). Persist a SHA-256 digest of the random token, never the raw token. Hashing a high-entropy random token with SHA-256 is different from password hashing. Cookie name `__Host-training_sid`, HttpOnly, Secure, SameSite=Lax, Path=/, no Domain; 7-day fixed expiry, with explicit logout/revocation. Use a separate non-__Host development cookie only on local HTTP. Do not expose the token to JavaScript or localStorage. Cookie expiry and DB expiry must agree, and check expiry on every authenticated request even if the TTL cleaner has not run.

CSRF: issue an unpredictable session-bound token, require it on authenticated state-changing requests and verify an exact allowed Origin. Login must also verify Origin and require JSON to prevent login CSRF; localhost origins are development-only. Configure reverse-proxy trust to the actual proxy/hop, not arbitrary forwarded headers. Rate-limit login by IP and normalized username with temporary backoff, generic credential errors and no permanent lockout. Suggested initial limits: 20/IP/15 min, 8/account/15 min; tune based on the proxy and tests. Avoid logging credentials or session cookies.

## HTTP and data

Use Helmet/CSP appropriate to same-origin React and click-loaded YouTube embeds (`https://www.youtube-nocookie.com`). No wildcard credentialed CORS, no `unsafe-eval`, no secrets in client environment variables. Check required iframe/player assets during browser tests. Use `frame-ancestors 'none'` for the app, while allowing its own YouTube iframe via frame-src. Keep authenticated responses and exports `Cache-Control: no-store`. Public assets may be cached by content hash. TLS via the existing proxy; secure cookies must work behind it.

Database credentials belong to a dedicated least-privilege application user scoped to this app database. Bootstrap/root credentials are separate. MongoDB listens only on a private Docker network or existing protected internal endpoint. Validate DTOs, IDs, numeric bounds and imported JSON. No arbitrary server-side URL fetching for video metadata. Limit request/import sizes. Redact auth data and private notes in logs.

## Before the first public push

Initialize Git in a clean sibling app folder and copy only `repo-input/`. Add exclusions immediately. Inspect staged files and any existing local history. Run a secret scanner and an explicit local check for the supplied password, bootstrap file, private profile, database URIs with passwords, private keys, exported health data and real workout records. Do not print matching secret values in scan output. Inspect the built frontend too. Use synthetic users/results in tests and screenshots. The generic exercise pack and source links can be public.

If a secret is accidentally committed locally, remove it from all local commits before the first push. If already pushed, stop propagation, rotate the affected secret and clean history; deleting only the working-tree file does not solve public exposure. Never publish the private handoff ZIP as a release asset.

## Backups and monitoring

Backups include credentials indirectly through DB hashes and personal workout data, so restrict and encrypt them. Reuse host backup infrastructure; establish a restore procedure and verify one restore into an isolated DB. Monitoring may check availability and resource use, but must not export personal set/weight/health data to third parties by default.
